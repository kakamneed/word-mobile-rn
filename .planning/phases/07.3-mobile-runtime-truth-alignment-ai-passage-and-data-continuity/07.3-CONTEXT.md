# Phase 07.3: Mobile runtime truth alignment, AI passage hookup, and data continuity - Context

**Gathered:** 2026-04-12
**Status:** Ready for planning

<domain>
## Phase Boundary

This inserted urgent phase converts the remaining mobile placeholder runtime into a trustworthy product surface. It focuses on replacing Android-side stub truth with the real bridge/backend path, aligning study/task semantics with the desktop reference, finishing AI passage/history integration, and defining how mobile user data should survive normal updates while offering a deliberate recovery path for reinstall or device migration.

It is not a broad redesign of every mobile screen, and it does not automatically expand scope into mandatory account sync. The priority is to stop shipping mock truth as if it were production behavior.

</domain>

<decisions>
## Implementation Decisions

### Runtime truth replacement
- **D-01:** The mobile app must stop relying on hardcoded Android stub payloads for Today, Plan, Study, Reports, Settings, and AI surfaces.
- **D-02:** The current `apps/mobile/android/app/src/main/java/com/wordmobile/WordCoreModule.java` stub is now the primary desktop-parity blocker; fixing isolated UI bugs on top of that stub is no longer acceptable.
- **D-03:** Mobile navigation and study launch must stop passing hardcoded `entrySourceIds` and synthetic `wordbookId` values from UI code.

### Study semantics and question contracts
- **D-04:** Mixed-test English-to-Chinese choice questions must be generated from Chinese meanings, not English distractor pools.
- **D-05:** Study question payloads must come from real entry data with meanings, phonetics, examples, and wrong-word metadata rather than placeholder source IDs.
- **D-06:** Mobile must follow the desktop repository at `D:\\projects\\word-desktop-tauri` as the canonical truth reference unless the user explicitly chooses to redefine product behavior.
- **D-07:** Based on the current desktop repository on 2026-04-12, the working assumption is: new-word/review = 4 questions per word, mixed test/wrong-word reinforcement = 3 questions per word, root/affix = 2 questions per item.
- **D-08:** The user's example of "5 new words -> 15 questions" conflicts with the current desktop repository. Phase 07.3 should plan against repository truth first and surface this conflict clearly rather than silently inventing a new rule.

### AI passage and review-center parity
- **D-09:** Mobile AI passage generation/history should match desktop's real wrong-word/today workflow rather than staying as mock text samples.
- **D-10:** AI passage remains optional and non-blocking; failures must stay visible but must not block the core study loop.
- **D-11:** Reports and wrong-word follow-up surfaces must stop presenting fabricated aggregates as persisted truth.

### Data continuity strategy
- **D-12:** Mobile user data should continue to live in the sandbox database under the platform app-data directory and must survive normal app updates.
- **D-13:** Reinstall, app-data clear, or device migration are separate recovery scenarios and should be handled through explicit backup/restore or sync design rather than assuming sandbox persistence alone is enough.
- **D-14:** Account login is not mandatory for v1 mobile continuity. The immediate phase should prioritize update-safe storage verification plus a practical local backup/recovery path.
- **D-15:** Account-backed backup/sync remains a v2 capability unless the user explicitly chooses to pull it forward.

### the agent's Discretion
- Exact native integration path used to connect React Native to the Rust bridge, as long as it removes stub truth from release behavior
- Exact mobile UI placement for AI passage entry/history once backed by real data
- Exact export/import UX or backup surface for non-account recovery, as long as it clearly communicates update-safe vs reinstall-safe guarantees

</decisions>

## Existing Code Insights

- Desktop already contains the full study-runtime truth for entry selection, question generation, wrong-word updates, snapshot completion, and AI passage history.
- Mobile already has a Rust bridge shell and path abstraction, so the work is not greenfield; the missing piece is replacing stub payloads with real backend-backed behavior.

### Established Patterns
- The project has repeatedly treated the desktop repository as the functional reference for migration work.
- Current mobile parity bugs cluster around places still driven by placeholders rather than real persisted state.
- The app is already local-first, and the requirements explicitly defer mandatory account sync to v2.

### Integration Points
- Bridge-truth replacement spans Android native module code, Rust bridge exports, shared app-core facades, and mobile TS clients.
- Study parity spans Today action resolution, study-session launch, question payload shaping, and session persistence.
- AI parity spans wrong-word input derivation, generation/history commands, renderer data, and mobile screen placement.
- Data continuity spans native path correctness, settings/visibility, update guarantees, and backup/recovery UX or documentation.

<specifics>
## Specific Ideas

- The user reported a concrete mixed-test bug where "choose Chinese meaning from English" still shows English options. The current Android stub fully explains this because mixed-test choice pools are hardcoded English regardless of question direction.
- The user wants mobile study counts and mode logic to match desktop semantics. Current mobile truth surfaces still use stub counts and hardcoded launch data, so this must be fixed at the runtime layer first.
- The user also asked whether account login is required to keep data. Current project requirements explicitly say mandatory account is a non-goal for v1; local continuity and optional backup should be planned before any account expansion.
- The current desktop repository on 2026-04-12 still implements 4 questions per new/review word. If the intended product truth is now 3 questions per word, that is a cross-platform behavior change and should be called out explicitly rather than assumed.

</specifics>

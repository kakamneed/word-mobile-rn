# Phase 07.3: Mobile runtime truth alignment, AI passage hookup, and data continuity - Research

**Date:** 2026-04-12
**Status:** Complete

## Goal

Determine the smallest executable plan that resolves the user's four newly reported issues without continuing to stack patches on top of placeholder mobile truth.

## Key Findings

### 1. Android is still shipping hardcoded product truth

Evidence:
- `apps/mobile/android/app/src/main/java/com/wordmobile/WordCoreModule.java`
- `apps/mobile/src/navigation/mobile-root.tsx`

Implication:
- Today, Plan, Study, Settings, and parts of the review flow are still powered by hardcoded JSON and fixed launch payloads.
- The mixed-test bug is not an isolated rendering issue; it is a direct symptom of the stubbed Android module generating the wrong options.
- Phase 07.3 should start by replacing or bypassing the stub truth layer.

### 2. The current shared mobile study facade is also still placeholder-level

Evidence:
- `crates/app-core/src/facade/study_facade.rs`
- `crates/study-core/src/question_builder.rs`

Implication:
- Even if the Android Java stub were removed, the current shared facade still builds words from `entry_source_ids` with placeholder word text and empty meanings/examples.
- Real parity requires porting desktop-grade entry loading and mode selection semantics into the shared/mobile path, not just swapping bridge transport.

### 3. Current desktop repository truth on 2026-04-12 is 4/4/3/3/2, not 3-question new-word loops

Evidence:
- `../word-desktop-tauri/apps/desktop/src-tauri/src/services/question_builder.rs`
- `../word-desktop-tauri/apps/desktop/src-tauri/src/commands/study.rs`

Implication:
- The current desktop repository still defines:
  - new-word = 4 questions per word
  - review = 4 questions per word
  - mixed test = 3 questions per word
  - wrong-word reinforcement = 3 questions per word
  - root/affix = 2 questions per item
- The user's "5 new words -> 15 questions" example conflicts with the current repository truth. Planning should assume repository parity first and explicitly note the conflict.

### 4. AI passage and report surfaces on mobile are still placeholders

Evidence:
- `apps/mobile/src/lib/ai-passage-client.ts`
- `apps/mobile/src/lib/reports-client.ts`
- `../word-desktop-tauri/apps/desktop/src/lib/ai-passage-client.ts`
- `../word-desktop-tauri/apps/desktop/src-tauri/src/commands/ai_passage.rs`

Implication:
- Mobile currently cannot claim AI passage/history parity because the client is returning mock passages and the reports client is returning fabricated aggregates.
- The required backend contracts and history behavior already exist on desktop and should be mirrored rather than reinvented.

### 5. Local SQLite in app-data is the right v1 storage base, but it does not solve reinstall/device migration by itself

Evidence:
- `.planning/REQUIREMENTS.md`
- `crates/platform-mobile/src/paths.rs`
- `crates/storage-core/src/persistence/mod.rs`

Implication:
- Saving `word.db` under the sandbox app-data directory is correct for local persistence and should survive normal app updates.
- Data loss after uninstall/reinstall or app-data clear is expected unless the product adds explicit backup/restore or account-backed sync.
- The project requirements explicitly defer mandatory account sync to v2, so 07.3 should plan a non-account continuity path first.

### 6. The highest-leverage split is runtime truth first, then parity features, then continuity hardening

Evidence:
- Stub truth affects study, today, plan, reports, and AI simultaneously
- Previous urgent phases 07.1 and 07.2 already closed UI-level gaps, but the parity audit still recorded runtime-truth gaps

Implication:
- Fixing the bridge/runtime layer first will collapse multiple visible bugs at once.
- AI/report hookup and backup/continuity should build on real persisted truth, not on mock state.

## Recommended Planning Shape

Phase 07.3 should be split into four executable plans:

1. Replace Android/mobile stub truth with real bridge-backed contracts
2. Align study mode sourcing, question generation, and session counts with desktop truth
3. Hook mobile AI passage/history and persisted report surfaces to backend truth
4. Harden local data continuity and define a non-account backup/recovery strategy

## Risks To Plan Around

- If the team continues fixing parity bugs inside the Java stub, more behavior drift will keep resurfacing.
- If the 3-question-vs-4-question new-word conflict is ignored, mobile may "match the request" while diverging from the current desktop repository.
- If AI/report screens are wired before runtime truth is fixed, the app will mix mock and real state in confusing ways.
- If data continuity is framed as "just add login," the project will accidentally pull a v2 sync initiative into urgent parity work.

## Planning Guidance

- Treat the current desktop repository as the source of truth unless the user explicitly asks to change product behavior across platforms.
- Remove hardcoded study launch data from navigation and hardcoded state from the Android module before doing more parity bug rounds.
- Expose a real settings/data-continuity surface so users can understand where local data lives and what survives update vs reinstall.
- Keep account-backed sync out of the urgent execution path unless the user deliberately re-scopes the project.

# Phase 07.1: Mobile parity and study correctness fixes - Research

**Date:** 2026-04-10
**Status:** Complete

## Goal

Determine the fastest and safest way to close the urgent mobile parity and correctness issues discovered during live phone testing.

## Key Findings

### 1. The mobile study bug is very likely caused by client-side mock/fallback logic, not only by backend truth

Evidence:
- `apps/mobile/src/lib/mobile-bridge.ts`
- `apps/mobile/src/lib/study-client.ts`
- `apps/mobile/src/screens/study/question-card.tsx`
- `apps/mobile/src/screens/study/study-session-screen.tsx`

Implication:
- The current mobile bridge still contains development fallback data and response shaping that can diverge from the real backend semantics.
- The Chinese-input correctness bug and blocked progression likely sit in the combination of mobile bridge payload shape, client response handling, and question-card assumptions.
- The fix should align the mobile flow more tightly with backend truth rather than patching only the visible UI.

### 2. Medical wordbook and root/affix mode are missing because mobile still uses placeholder vocabulary and incomplete mode exposure

Evidence:
- `apps/mobile/src/lib/vocabulary-client.ts`
- `apps/mobile/src/screens/onboarding/onboarding-flow.tsx`
- `apps/mobile/src/screens/plan/wordbook-selector-section.tsx`

Implication:
- The mobile app is still using placeholder wordbook data instead of the full shared vocabulary universe.
- Restoring medical and root/affix parity likely requires updating vocabulary client data flow, onboarding selection, plan selection, and study entry routing.

### 3. Chinese copy normalization can be fixed pragmatically without introducing a full localization system

Evidence:
- `apps/mobile/src/screens/onboarding/onboarding-flow.tsx`
- `apps/mobile/src/screens/study/question-card.tsx`
- `apps/mobile/src/screens/today/*`
- `apps/mobile/src/screens/plan/*`
- `apps/mobile/src/screens/library/*`

Implication:
- The current mobile build contains many visible English strings and a few mixed/garbled remnants.
- An urgent pass can normalize the most visible user-facing surfaces to Chinese without designing a complete i18n framework.

### 4. This urgent phase should focus on mobile trust recovery, not broad feature work

Evidence:
- The user reported the app now opens, so this is no longer a startup bootstrap problem.
- The reported issues all directly affect user trust in learning correctness or parity.

Implication:
- The highest priority item is the study correctness bug.
- The parity items should then restore confidence that the mobile app actually reflects the real product scope.
- This phase should avoid broad architectural churn unless it is necessary to fix the reported defects.

## Recommended Planning Shape

Phase 07.1 should be split into three executable plans:

1. Restore missing mobile learning content parity: medical wordbook + root/affix mode
2. Normalize visible mobile product copy to Chinese
3. Fix Chinese-input answer correctness and next-question progression using backend-aligned study semantics

## Risks To Plan Around

- If the study correctness fix only patches UI text, the underlying answer semantics may remain wrong.
- If parity is restored only in list surfaces but not in plan/study entry paths, users will still experience missing capability.
- If copy cleanup is too broad, it can distract from the urgent correctness work.

## Planning Guidance

- Prioritize the Chinese-input study bug first in execution ordering, even if planning is grouped differently.
- Make medical and root/affix parity visible anywhere users choose study content or plan scope.
- Normalize the most visible mobile surfaces to Chinese in a pragmatic pass.
- Keep the phase tightly scoped to the four reported phone issues.
